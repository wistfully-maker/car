# speech_command 完整任务指令识别设计

## 1. 目标

修复长比赛指令尚未说完时，`speech_command` 就匹配原厂 QA、播放串口反馈并停止
录音的问题。

比赛任务指令必须在取得两个目标母类后只发布一次 `/question`。识别过程中的短文本、
唤醒词尾音和单母类片段不得触发串口复述或停止录音。

## 2. 根因

当前云端 IAT 回调会处理每一个非空结果，但没有用 `ls` 控制完成时机。每次回调都会：

1. 把当前文本写入 `question`；
2. 调用 `FindDocument` 和 `QA_list_` 做精确或模糊匹配；
3. 匹配成功后发送串口协议；
4. 调用 `gStop()`。

所以“请前往物品领取区取得电子产品”这样的不完整片段也会触发预设反馈，反馈音和
停止操作会截断后半句。

## 3. 方案

将云端识别结果分为以下类型：

### 3.1 比赛任务候选

满足以下任一特征的文本进入比赛任务候选：

- 包含“物品领取区”或“领取区”；
- 包含“仿真环境”。

比赛任务分支不调用 `FindDocument`，不查询 `QA_list_`，不发送原厂 QA 串口反馈。
候选已经开始后，后续母类和“对应仓库”片段继续合并到当前候选。

### 3.2 非比赛文本

比赛版本不再使用原厂 QA。没有比赛任务特征的云端 IAT 文本只记录并忽略，不调用
`FindDocument`、`QA_list_`、串口回复或自动 TTS。“小飞小飞”的硬件唤醒链路保持
不变；最终结果播报仍由编排器的独立 TTS 链路完成。

## 4. 完整性判定

比赛任务文本同时包含以下内容时才算完整：

- “食品”“日用品”“电子产品”中两个不同的母类；
- 表示实物任务的领取区语义；
- “仿真环境”语义；
- 两次“对应仓库”，分别对应实物任务和仿真任务。

判定以语义完整性为主，不强制等待 `ls == true`。实测中完整长句可能以
`ls == false` 返回；若只依赖 `ls`，会漏掉已经完整的任务。

识别结果尚不完整时：

- 不发布 `/question`；
- 不发送串口反馈；
- 不调用 `gStop()`；
- 保持监听，等待后续识别结果。

识别结果完整时：

1. 发布一次完整 `/question`；
2. 记录本轮已发布状态，忽略同一轮重复结果；
3. 不进行原厂 QA 复述；
4. 调用 `gStop()`，等待下一次唤醒。

## 5. 文本累积

维护当前唤醒轮次的候选文本：

- 新结果包含比旧候选更完整的文本时，使用新结果；
- 新结果是独立后续片段时，追加到候选文本；
- 自动剥离前部可能附带的“飞”“小飞”“小飞小飞”；
- 用户在错误识别后重新说出一条包含领取区和母类的新任务时，以新任务替换旧候选；
- 新唤醒时清空候选文本和“已发布”标记；
- 停止、错误或会话结束且仍不完整时清空候选，不发布任务。

第一版只处理当前比赛所需的三个固定母类，不引入通用自然语言状态机。

## 6. 与编排器的边界

`speech_command` 只负责得到完整文本并发布 `/question`。

后续职责保持不变：

```text
/question
 -> voice_task_adapter 提取两个母类
 -> task_orchestrator 编排任务
 -> QR 与 LLM
 -> TTS 按比赛规定格式播报最终推理结果
```

因此，识别阶段不应复述用户命令。正式语音播报只由编排器在 LLM 完成后触发。

## 7. 验收标准

### 自动测试

- 唤醒词尾音“飞”不发布任务、不停止；
- 只有“请前往领取区”时不发布、不停止；
- 只有一个母类时不发布、不停止；
- 两个母类但没有仿真环境语义或不足两次“对应仓库”时不发布；
- 完整双目标指令只发布一次；
- 完整任务不发送 QA 串口协议；
- 普通非比赛文本不触发原厂 QA；
- 下一次唤醒能够开始新的任务轮次。

### 实机测试

连续三轮说出包含不同母类组合的完整指令：

- 三轮都只产生一条有效完整 `/question`；
- 没有中途复述用户指令；
- 没有提前停止；
- 每轮完成后均能再次唤醒；
- 三轮均被 `voice_task_adapter` 正确解析为两个母类。

## 8. 暂不处理

- 串口短分片与极端并发的进一步鲁棒性加固；
- 唤醒提示音偶发缺失；
- 通用 ASR 纠错或大模型文本修复；
- 导航模块问题。

以上内容在本次语音完整性修复和三轮验收通过后分别处理。
