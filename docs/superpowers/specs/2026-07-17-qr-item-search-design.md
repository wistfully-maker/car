# U-CAR-02 二维码物品搜索第一版设计

## 1. 目标

在固定物品领取区内，让 U-CAR-02 通过车身原地旋转，使前置摄像头依次朝向三面固定墙壁，识别每面墙上的普通二维码，访问二维码中的网址并从返回 JSON 中取得物品名称。

第一版以可靠跑通完整搜索流程为目标，不优化竞速时间，也不实现语音识别、Spark X2 推理、物品分类和后续导航。模块需要为这些后续能力保留明确接口。

## 2. 场景与假设

- 物品领取区由三面固定墙壁构成，每面墙上有一个二维码。
- 摄像头固定朝向车头，随车身一起旋转。
- 二维码内容是一个网址。
- 访问网址后预期得到以下 JSON：

```json
{
  "code": 200,
  "result": "香蕉"
}
```

- 比赛时只需找到语音任务指定的一个物品，不要求扫描完三个二维码。
- 第一版尚未接入语音和 LLM，因此搜索控制器通过外部“匹配/继续”结果决定是否提前停止；调试模式可以选择扫描一整轮并记录所有结果。
- 摄像头节点、底盘控制和定位系统由现有 ROS 环境提供。

## 3. 方案选择

第一版采用“固定朝向、停稳识别”方案：

1. 小车抵达物品区观察位置。
2. 调整至第一面墙的观察朝向。
3. 停止运动，等待画面稳定。
4. 识别二维码并解析物品名称。
5. 若上层判定匹配，则结束搜索。
6. 若不匹配、二维码内容处理失败或本朝向始终未识别到二维码，则转向下一面墙。
7. 三面墙均检查后仍未匹配，则报告本轮失败。

暂不采用连续旋转识别，因为运动模糊、制动距离和曝光变化会增加第一版调试难度。模块仍采用连续图像输入和非阻塞状态机，便于后续升级为低速连续扫描。

## 4. ROS 模块

### 4.1 `qr_scanner`

职责：

- 订阅相机图像话题，默认 `/usb_cam/image_raw`。
- 使用 `cv_bridge` 转换为 OpenCV 图像。
- 使用 `cv2.QRCodeDetector` 解码普通二维码。
- 对同一解码内容进行连续帧确认和短时去重。
- 校验二维码内容是否为 HTTP/HTTPS 网址。
- 请求二维码网址并解析 JSON。
- 校验 `code == 200` 且 `result` 为非空字符串。
- 发布结构化扫描结果。

该模块不控制车身运动，也不判断物品类别。

建议结果字段：

- `url`：二维码原始网址。
- `item_name`：JSON 中的 `result`。
- `wall_index`：当前观察墙面编号，由控制器提供。
- `status`：`success`、`decode_timeout`、`http_error`、`invalid_json` 或 `invalid_payload`。
- `message`：便于现场调试的错误说明。

### 4.2 `item_search_controller`

职责：

- 接收开始搜索指令。
- 控制 `/cmd_vel`，依次转向三面墙。
- 每次旋转结束后发布零速度，并等待图像稳定。
- 通知 `qr_scanner` 开启当前墙面的有效识别窗口。
- 接收扫描结果并转交上层目标判断模块。
- 根据上层返回的“匹配”或“不匹配”决定结束或继续。
- 管理超时、失败和紧急停止。

第一版旋转控制优先使用里程计或 IMU 航向闭环，不单纯依赖固定时间。若现有系统无法提供稳定航向，则允许在调试阶段使用低速定时旋转，但不作为最终比赛方案。

### 4.3 `target_matcher` 接口

第一版不实现 LLM，只定义接口：

- 输入：当前物品名称，以及未来由语音模块提供的目标描述。
- 输出：`matched`、`not_matched` 或 `error`。

调试时支持人工确认或“扫描全部三面墙”模式。后续接入 Spark X2 时替换匹配实现，不修改扫码和旋转模块。

## 5. 状态机

```text
IDLE
  -> TURNING
  -> SETTLING
  -> SCANNING
      -> WAITING_MATCH
          -> SUCCESS                 匹配
          -> TURNING                 不匹配且仍有下一面墙
          -> NOT_FOUND               不匹配且三面墙已检查
      -> TURNING                     二维码处理失败且仍有下一面墙
      -> NOT_FOUND                   最后一面墙二维码处理失败
      -> TURNING                     当前墙面扫描超时且仍有下一面墙
      -> NOT_FOUND                   最后一面墙扫描超时
  -> ERROR                           底盘、图像或内部异常
```

任何状态收到停止指令时，控制器必须立即发布零速度并回到 `IDLE`。

## 6. 识别与网络策略

- 仅在 `SCANNING` 状态处理二维码，避免转动过程中误触发。
- 同一内容需在多个近邻帧中稳定出现后才确认，默认连续 2 帧，可配置。
- 每面墙只接受第一个稳定二维码结果。
- 一旦获得稳定二维码内容，本墙面的识别窗口立即结束；处理成功则等待匹配结果，处理失败则记录原因并立即转向下一面墙，不再等待本墙面扫描超时。
- URL 请求设置连接和读取超时，不允许无限等待。
- 网络失败采用有限重试，默认 2 次。
- 一次搜索周期内对已成功解析的 URL 去重。
- HTTP 请求不得阻塞相机回调；使用工作线程或任务队列处理。
- 日志保留时间、墙面编号、网址、响应状态、物品名称和失败原因。

## 7. 旋转与稳定策略

- 旋转速度、目标角度、角度容差、停稳等待时间均使用 ROS 参数配置。
- 第一版使用较低角速度，确保不会越过目标朝向。
- 抵达目标角度后连续发布零速度。
- 等待固定稳定窗口后再开启识别，初始建议 0.5 至 1 秒。
- 三面墙的相对朝向由现场标定结果配置，不假定严格相差 90 度。
- 若航向反馈超时或旋转超过最大持续时间，立即停止并进入 `ERROR`。

## 8. 异常处理

- 无图像：报告相机输入超时，不启动车身搜索。
- 未识别到二维码：当前墙面超时后继续下一面。
- 解码内容不是网址：记录无效内容并立即进入下一面墙。
- HTTP 或 JSON 错误：有限重试后记录错误并立即进入下一面墙。
- 三面墙均无匹配：发布 `NOT_FOUND`，停车并等待上层决策。
- ROS 关闭、节点异常或人工停止：确保最后发送零速度。

## 9. 第一版验收标准

### 离线识别

- 能从包含比赛样式二维码的清晰图像中解码网址。
- 能正确解析正常 JSON 并取得 `result`。
- 对超时、非 JSON、`code != 200`、缺少 `result` 等情况给出明确状态。
- 同一二维码在连续帧中只生成一次有效结果。

### 小车联调

- 小车可以按三个配置朝向依次旋转并停稳。
- 旋转过程中不会触发有效识别。
- 每面墙停稳后能够识别二维码并输出物品名称。
- 模拟上层返回匹配时，小车立即结束搜索并保持停车。
- 三面墙均未匹配或未识别时，小车停车并发布 `NOT_FOUND`。
- 任意阶段执行停止操作时，小车能够停止。

## 10. 后续竞速优化

第一版稳定后，再按测量数据逐项优化：

- 缩短停稳等待时间。
- 根据曝光和清晰度动态判断画面是否稳定。
- 允许低角速度连续扫描。
- 扫描到候选二维码后减速而非完全固定停靠。
- 根据目标墙面历史和入口方向优化扫描顺序。
- 将网络请求、LLM 推理与底盘下一步准备并行化。

这些优化不改变二维码解析结果接口和上层匹配接口。
