# U-CAR-02 连续旋转二维码搜索升级设计

## 1. 背景与目标

现场规则和实测推翻了旧版“固定三面墙、每转到一个预设角度后停车扫码”的核心假设：

- 三个二维码会随机放置在物品领取区四条边的任意位置，每条边最多一个，入口和出口区域禁止放置。
- 机器人必须依次识别并读取三个二维码的全部内容，不能找到一个目标物品后提前结束。
- 二维码不一定处于墙面中央或严格相隔 90°。
- 旧版旋转速度偏低，停车等待造成额外耗时。
- 户外太阳光可能造成画面过曝，单一预设朝向容易错过二维码。

本次升级的目标是：机器人在观察点连续原地旋转，同时解码视野中的二维码；取得三个不同二维码对应的物品名称后停车并输出有序结果。如果首轮未取得三个结果，只对可能漏扫的方向做低速定向补扫。

本次只升级二维码搜索包并保留跨模块接口，不实现真实语音、Spark X2 调用、TTS 和后续导航。

## 2. 设计原则

- 第一版优先完整跑通流程，不以最短耗时作为验收门槛。
- 搜索不依赖二维码位于预设墙面中心。
- 旋转、图像解码和 HTTP 请求互不阻塞。
- 三个二维码全部取得后才报告成功。
- 首轮遗漏时利用已记录的角度和图像质量定向补扫，不盲目重复完整慢速旋转。
- 自动靠近墙面属于后续增强，不纳入本次实现。
- 任一结束状态都必须保证底盘停车。

## 3. 总体架构

保留两个 ROS 节点，但重新划分内部职责。

### 3.1 `item_search_controller`

负责：

- 接收结构化搜索启动和停止消息。
- 从里程计或 IMU 获取航向，累计本次搜索的旋转角度。
- 在首轮以固定角速度连续旋转约 380°。
- 将当前搜索阶段和相对航向提供给扫码节点。
- 根据扫码进度提前结束旋转或生成补扫区间。
- 在定向补扫阶段控制低速转向。
- 管理总超时、航向超时、底盘错误和安全停车。
- 汇总扫码节点提供的结果，按首次发现顺序发布最终搜索结果。

### 3.2 `qr_scanner`

负责：

- 持续接收相机最新帧，只保留最新待处理帧，避免处理积压的旧图像。
- 在搜索激活期间持续执行二维码检测和解码。
- 校验解码字符串为 HTTP 或 HTTPS URL。
- 按 URL 去重并记录首次发现顺序、航向和图像质量。
- 将新 URL 放入独立 HTTP 任务队列。
- 并发请求网址、解析 JSON 并取得 `result`。
- 记录每个角度分区的亮度、过曝比例、清晰度和是否成功解码。
- 在补扫阶段对最新帧进行有限的增强后再次解码。

二维码包不接收语音目标、不判断物品类别，也不调用 LLM。跨模块协议见 `2026-07-19-task1-minimal-integration-protocol.md`。

## 4. 首轮连续扫描

### 4.1 旋转范围

机器人从任意观察起始朝向开始，以相对累计航向控制旋转。首轮目标覆盖角为 380°，而不是精确 360°，用额外 20°覆盖起步加速、航向误差和起点附近可能被跳过的画面。

四条边只是二维码可能出现的空间约束，不转换为四个固定停车朝向。只要二维码进入相机视野，扫码节点就立即尝试解码。

### 4.2 初始参数

| 参数 | 默认值 | 说明 |
| --- | ---: | --- |
| `fast_angular_speed` | `0.40 rad/s` | 首轮连续旋转速度 |
| `targeted_angular_speed` | `0.20 rad/s` | 定向补扫速度 |
| `minimum_effective_speed` | `0.11 rad/s` | 克服当前底盘角速度死区 |
| `fast_sweep_angle` | `6.63 rad` | 约 380° |
| `expected_qr_count` | `3` | 成功所需不同 URL 数 |
| `heading_timeout` | `1.0 s` | 航向数据最大允许间隔 |
| `search_total_timeout` | `40.0 s` | 二维码包内部搜索上限 |
| `http_connect_timeout` | `1.0 s` | 单次连接超时 |
| `http_read_timeout` | `2.0 s` | 单次读取超时 |
| `http_retry_count` | `1` | 首次失败后的额外尝试次数 |
| `http_worker_count` | `3` | 最大并发网址请求数 |

这些值是第一次场地联调的起点，不是最终比赛参数。角速度仍需用真实二维码、真实距离和现场光照验证；如果帧中二维码运动模糊，应先降低至 `0.30 rad/s`，而不是改变状态机。

### 4.3 提前结束

首轮旋转过程中，如果三个不同 URL 均已解码，控制器无需完成 380°，立即减速并停车。停车后只等待尚未完成的 HTTP 请求。

“URL 已解码”和“物品 JSON 已解析”是两个不同事件。提前结束旋转以取得三个不同 URL 为条件，不等待网络响应完成。

## 5. 解码与异步 HTTP

### 5.1 单帧接收策略

旧版连续两帧确认会在旋转中缩短有效识别窗口。本版在解码器成功返回完整字符串后立即接收单帧结果，再通过以下条件过滤误识别：

- 解码结果非空。
- URL scheme 只能是 `http` 或 `https`。
- URL 必须包含主机名。
- 本次搜索中该 URL 尚未出现。

二维码自身具有纠错和格式校验，结合严格 URL 校验后，第一版不再强制连续两帧一致。若现场出现误 URL，再增加可配置的多帧确认，默认保持关闭。

### 5.2 去重和顺序

同一 URL 在一次搜索中只创建一个条目和一个 HTTP 任务。条目在首次解码时立即分配递增的 `order`，并记录 `detected_yaw`。最终结果始终按这个首次发现顺序输出，不按 HTTP 完成顺序排序。

不同 URL 即使返回相同 `result`，仍视为两个不同二维码并保留两个条目。比赛要求读取三个二维码，因此成功条件是三个不同 URL 均得到有效响应。

### 5.3 HTTP 任务

相机回调不得执行网络请求。扫码节点维护独立任务队列，并使用最多三个工作线程并发请求三个 URL。

合法响应必须同时满足：

- HTTP 请求成功。
- 响应体为 JSON 对象。
- `code` 的数值为 `200`。
- `result` 为去除首尾空白后仍非空的字符串。

请求失败或负载无效时，按配置重试一次。重试仍失败的 URL 保留错误状态；只要仍在总搜索时限内，控制器允许在后续画面中发现其他 URL，但不会对同一失败 URL 无限创建任务。

首轮已取得三个 URL 但其中某个 URL 最终解析失败时，搜索不能报告 `complete`。控制器应进入定向补扫，并允许失败 URL 在补扫阶段额外请求一次；一个 URL 在整次搜索中最多请求三次（首次、常规重试、补扫重试）。由于赛场实际只有三个二维码，额外发现的第四个 URL 不作为恢复失败响应的前提。

## 6. 图像质量记录与定向补扫

### 6.1 角度分区

将相对 360° 划分为 24 个 15° 分区。搜索期间每个有效帧按当前相对航向归入一个分区，并累计：

- 帧数量。
- 灰度均值。
- 高亮像素比例，用于判断过曝。
- 拉普拉斯方差，用于估算清晰度。
- 是否至少出现过一个有效 URL。

分区统计只用于选择补扫方向和日志诊断，不作为首轮解码的前置条件。

### 6.2 候选补扫区间

首轮结束仍不足三个有效结果时，控制器从以下分区生成补扫候选：

1. 没有收到足够帧的未覆盖分区。
2. 过曝比例高或清晰度低的低质量分区。
3. 已发现 URL 的分区左右相邻区域，用于覆盖二维码处于视野边缘的情况。
4. 首轮起始角附近的重叠区。

相邻候选分区合并为区间，并按“未覆盖优先、低质量其次、已发现二维码邻域再次”的顺序补扫。每个区间在两侧额外增加 10° 边界，避免精确分区边缘漏检。

控制器允许转向最近的候选区间，再以 `targeted_angular_speed` 穿过该区间。取得三个不同有效结果后立即停车。所有候选区间完成仍不足三个时报告 `not_found`。

### 6.3 补扫图像增强

首轮只对原始帧解码，保持吞吐量。定向补扫时对同一最新帧按以下有限序列尝试：

1. 原始图像。
2. 灰度图。
3. CLAHE 局部对比度增强。
4. 自适应阈值图。

任一版本成功后停止处理该帧。处理器仍只消费最新帧；如果处理期间新帧到达，旧的排队帧被替换，避免因增强处理导致延迟持续累积。

## 7. 光照策略

软件不能恢复传感器已经完全过曝而丢失的二维码纹理。因此第一版采用“检测并补扫”，不承诺通过后处理修复白屏：

- 日志记录分区过曝比例和亮度。
- 过曝区进入定向低速补扫。
- 场地测试时调整观察点或起始朝向，尽量避免镜头正对太阳。
- 二维码应保持平整、无透明反光覆膜；摄像头可加遮光罩。

固定曝光、自动曝光锁定或 V4L2 参数控制需要先确认当前 `usb_cam`、摄像头驱动和室内外曝光范围。本次代码结构为后续曝光控制保留参数，但不在没有实测数据时强制设置。

## 8. 状态机

```text
IDLE
  -> FAST_SWEEP
       -> WAITING_HTTP          已解码 3 个不同 URL
       -> TARGETED_RESCAN       首轮结束但有效结果不足 3 个
       -> ERROR                 航向、相机、底盘或内部异常

TARGETED_RESCAN
  -> WAITING_HTTP              已解码 3 个不同 URL
  -> COMPLETE                  3 个 URL 均解析成功
  -> NOT_FOUND                 候选区间耗尽或总超时
  -> ERROR

WAITING_HTTP
  -> COMPLETE                  3 个 URL 均解析成功
  -> TARGETED_RESCAN           存在最终解析失败且仍可补扫
  -> NOT_FOUND                 总超时
  -> ERROR
```

控制器在 `FAST_SWEEP` 和 `TARGETED_RESCAN` 之外不允许发布非零速度。收到停止消息、ROS 关闭、进入任何终态或捕获未处理异常时，均发布零速度。

## 9. 结果和跨模块边界

二维码包通过 `/qr_item_search/result` 发布协议版本 1 的 JSON。搜索成功必须包含三个条目，每项至少包含：

- `order`
- `item_name`
- `url`
- `detected_yaw`

旧版逐墙面的 `wall_index` 和逐物品的 `match_decision` 不再属于主流程。为了避免两个行为并存造成歧义，本次升级直接替换旧搜索模式，不维护固定墙面兼容模式。

LLM 需要的目标大类不传入二维码包。未来的 `task1_orchestrator` 在二维码搜索成功后，将三个 `item_name` 和语音目标大类组合为 LLM 请求。

## 10. 异常处理

- **无相机帧**：启动后在配置时间内无图像，停车并发布 `error`。
- **航向超时**：立即停车并发布 `error`，不得退化为无边界定时旋转。
- **二维码不足三个**：完成所有定向补扫后发布 `not_found`，并带上已经成功解析的部分结果。
- **重复二维码**：按 URL 去重，不增加计数，不延长当前区间。
- **无效 URL**：记录调试日志并忽略，不创建 HTTP 请求。
- **HTTP 或 JSON 错误**：有限重试；最终失败时保留错误信息并继续寻找其他有效 URL。
- **总超时**：停车，根据已取得结果发布 `not_found` 或 `error`；正常搜索未凑齐三个时使用 `not_found`。
- **停止请求**：立即停车并发布 `stopped`。

## 11. 测试方案

### 11.1 Windows 本地单元测试

- 单帧合法 URL 能立即被接收。
- 非 HTTP(S)、缺少主机名和空字符串被拒绝。
- 重复 URL 只创建一个条目和一次请求。
- 三个 HTTP 任务可以并发完成，最终仍按发现顺序输出。
- 正常、超时、非 JSON、`code != 200`、空 `result` 均有确定结果。
- 分区统计正确处理 0°/360° 边界。
- 补扫候选能合并相邻低质量分区并增加边界。
- 最新帧替换策略不会积压图像。
- 任何终态的控制输出为零速度。

### 11.2 ROS 模拟测试

- 用录制图像或测试二维码模拟旋转视野，在不同非 90° 航向发现三个二维码。
- 在 HTTP 返回顺序与发现顺序相反时验证最终排序。
- 模拟一个过曝分区，验证首轮后进入该方向的低速补扫。
- 模拟只有两个二维码，验证最终 `not_found` 和部分结果。
- 重复发送同一个 `search_id`，验证不会启动第二次旋转。

### 11.3 小车场地测试

- 从观察点连续旋转时能够边转边识别，不再依赖停车朝向。
- 三个二维码分别随机放在四边中的三边，且不位于墙面中央时能全部读取。
- 取得第三个 URL 后能够提前停车。
- 手机屏幕展示和打印二维码分别验证；正式判断以打印二维码为准。
- 顺光、侧光和可能过曝的方向分别记录帧率、识别角度和图像质量。
- 人工停止、相机断流和航向中断时车辆均能停车。

## 12. 第一版验收标准

- 搜索过程中持续解码，不等待固定墙面停车。
- 不假定二维码严格位于三个或四个预设方向。
- 一次搜索只对不同 URL 计数，并要求三个 URL 都得到合法物品结果。
- HTTP 请求不阻塞相机解码或底盘旋转。
- 最终项目按首次识别顺序输出，不受网络返回顺序影响。
- 首轮不足三个时进入基于覆盖和图像质量的定向补扫。
- 补扫结束仍不足三个时停车并报告部分结果和明确原因。
- 终止、异常和 ROS 关闭时可靠发布零速度。
- 使用最小集成协议的模拟语音和模拟 LLM 能完成接口联调。

## 13. 明确延期的能力

以下能力保留设计空间，但不进入本次实现和验收：

- 根据已识别二维码的空间位置推断漏扫二维码并自动靠近某面墙。
- 使用 LiDAR、地图和 `move_base` 执行领取区内的二次观察位移动。
- 自动控制摄像头曝光或在旋转过程中动态调节曝光。
- Spark X2、真实语音识别、TTS 和目标车间导航。
- 为极限竞速进行连续运动轨迹、扫描顺序和网络/导航并行优化。
