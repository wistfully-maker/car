# U-CAR 方向里程计与导航控制周期稳定化设计

## 1. 范围与目标

本阶段只处理两个已经由实测证据支持的问题：

1. 底盘顺、逆时针旋转的里程计误差不对称；
2. `move_base` 配置为 10 Hz，但实测 `/cmd_vel` 和 TEB 局部路径长期只有约
   3～4 Hz，并伴随控制循环和代价地图更新超期。

本阶段不调整地图质量，不继续试探 TEB 几何和障碍参数，不修改二维码模块的实际旋转
速度。底盘命令超时统一采用 `cmd_timeout: 0.5`。

## 2. 已有证据

- 约 0.50 m 直线测试中，里程计约为 0.5004 m，当前
  `wheel_radius: 0.04657` 保持不变。
- 顺时针整圈测试的里程计累计角约为 359.210°，实车视觉误差约 1～2°。
- 两次逆时针测试均出现约 5°的同方向误差，说明误差具有方向相关性，而不是一次摆放
  或拍照误差。
- 导航 bag 中 `/cmd_vel` 约为 3.86 Hz，TEB局部路径约为 3.54 Hz；日志多次出现
  control loop 和 costmap update missed rate。
- 当前 `base_driver` 使用两个异步回调线程，但仍需区分耗时来自 TEB、costmap、TF、
  整机CPU还是底盘串口执行链。

## 3. 方案选择

采用“只修正发布里程计 + 先测量后优化控制周期”的最小改动方案。

暂不采用以下方案：

- 不引入 `robot_localization/EKF`，避免在尚未验证IMU数据与协方差前增加新的TF所有者；
- 不修改电机指令到四轮转速的逆运动学，避免改变真实旋转速度和二维码模块行为；
- 不先降低 `controller_frequency` 来消除告警，因为这不会解决实际命令输出断续。

## 4. 方向相关里程计修正

### 4.1 参数

在 `base_driver` 增加私有参数：

```yaml
odom_angular_scale_ccw: 0.986
odom_angular_scale_cw: 1.000
```

参数缺失时均默认 `1.0`，以保持旧行为并便于回退。

### 4.2 数据流

```text
编码器脉冲
  -> 原始四轮速度
  -> 原始 Vx/Vy/Vth
  -> 按 Vth 正负选择角速度修正系数
  -> corrected_Vth
  -> 姿态积分和 /odom.twist.twist.angular.z
  -> /odom 与 odom -> base_link
```

只修正 `Vth` 以及由它计算的 `delta_th`。`Vx/Vy`、编码器读数、`/cmd_vel` 到四轮
目标速度的计算全部保持不变。

ROS中正角速度为逆时针，因此：

- `Vth > 0` 使用 `odom_angular_scale_ccw`；
- `Vth < 0` 使用 `odom_angular_scale_cw`；
- `Vth == 0` 不做方向修正。

启动日志必须打印两个实际加载的系数，避免误判配置是否生效。

### 4.3 简化验证

第一轮只进行一次逆时针原地旋转：

- 使用现有一次性标定脚本和清晰地面基准线；
- 确认修正方向正确；
- 目标是把原来约 5°的误差明显压缩，初始验收允许人工测量精度有限；
- 若误差反而增大，立即恢复系数 `1.0`，不进入导航测试。

随后进行多轮同路线导航集成验证，观察：

- 转弯后雷达扫描与静态墙面是否继续明显错位；
- `map -> odom` 是否仍出现持续同方向的大幅修正；
- AMCL是否发生明显跳变；
- 是否再次因定位漂移导致局部轨迹不可行。

导航结果用于集成验收，但不能完全替代一次逆时针定量旋转，因为AMCL可能暂时掩盖
错误里程计。

## 5. `cmd_timeout` 单一来源

比赛与后续测试统一采用：

```yaml
cmd_timeout: 0.5
```

当前 `driver_params_ucarV2.yaml` 与 `robot_base_bringup.launch` 存在两个来源。实现时保留
一个明确来源，并在启动后通过以下命令确认实际值：

```bash
rosparam get /base_driver/cmd_timeout
```

本阶段不再比较 `0.2` 与 `0.5`。

## 6. 控制周期诊断

在修改性能参数前，采集同一路线的轻量诊断数据：

- `/cmd_vel`、TEB局部路径、`/scan`、`/odom` 和必要TF的频率与最大间隔；
- `move_base`、`amcl`、`ydlidar_node`、`base_driver` 的CPU和内存占用；
- 控制循环与costmap更新超期次数；
- TEB轨迹不可行、规划失败和主动零速度次数；
- `/cmd_vel` 中零速度占比；
- 系统整体负载。

诊断工具只订阅和记录，不发布速度，不改变参数。

## 7. 根因分支与最小修复

### 7.1 TEB计算耗时

若单次局部规划耗时占主导，按单变量顺序验证：

1. 启用TEB多线程；
2. 在不改变障碍距离、footprint和速度上限的前提下减少优化计算量；
3. 检查局部路径点数和前视距离造成的优化规模。

### 7.2 Costmap耗时

若costmap更新时间占主导，优先降低非必要发布频率，再评估局部窗口和障碍数据规模。
不得为了提速删除障碍层或缩小安全footprint。

### 7.3 TF或时间戳等待

若存在TF外推、等待或消息时间戳不连续，先修复发布链和时钟问题，不通过继续增大
`transform_tolerance`掩盖。

### 7.4 TEB主动输出零速度

若控制循环实际正常，但TEB因轨迹不可行反复输出零速度，则将其归类为规划可行性问题，
不能误判为CPU频率问题。本阶段只记录证据，不同时重新调整整套TEB参数。

### 7.5 底盘执行链断续

若 `move_base` 能持续发布而实车仍一走一停，则检查串口发送循环、命令保活和底盘最小
有效速度。此时不修改TEB优化频率。

## 8. 控制周期验收

优先目标为：

- `/cmd_vel` 长期稳定达到至少 8 Hz；
- 不再持续出现控制循环超期；
- 最大命令间隔显著小于 `cmd_timeout: 0.5`；
- 直线和弯道不因命令间歇归零而一走一停；
- 修改前后使用同一路线、同一地图和同一导航参数比较。

如果证据证明现有硬件无法稳定维持10 Hz，才将 `controller_frequency` 设置为实测可以
长期维持的频率，例如5 Hz，并同步检查底盘在该周期下是否能连续执行。配置值必须与
实际能力一致。

## 9. 实施与回退顺序

1. 将小车当前 `ucar_controller` 源码同步到独立本地工作区并建立基线提交；
2. 为方向选择和缩放逻辑编写离线测试；
3. 实现两个方向参数，不修改指令运动学；
4. 统一 `cmd_timeout: 0.5`；
5. 本地编译和测试后部署；
6. 进行一次逆时针旋转验收；
7. 采集一轮控制周期诊断；
8. 依据证据只实施一个性能修正；
9. 多轮导航验证雷达框漂移和行驶连续性。

任何阶段均可通过把两个角速度系数恢复为 `1.0` 回退里程计行为。性能参数每次只修改
一个，并保存修改前参数快照和测试日志。
